# Automation node experiment — 2026-07-19

> Historical comparison only. The synthetic reference-copy recipe is superseded by
> `../file-projections/RESULTS-2026-07-19.md`, which measures native standalone-binary
> context/path/change plan/change apply operations.

## Decision

Use task-specific file projections as executable concept recipes for repeated feature
shapes. Keep a concise generic `context.md` as fallback orientation. Do not expect a code
graph or prose projection alone to stop a tool-rich model from rediscovering the repo.

The verified file-projection recipe is the clear winner: **1 read, 1 API call, 2,758 raw
tokens, and 1.6 seconds to first edit; 15,872 total tokens; 100/100 quality**. It matches
the independent reference implementation while using 169x fewer raw tokens before edit,
34x fewer pre-edit reads, 48x less wall time to edit, and 64x fewer total raw tokens than
baseline.

This winning arm is explicitly a semantic-reuse test, not free-form code generation. The
pure generative file-projection arm also won among free-form arms on total tokens and
quality, but failed hidden API-shape acceptance.

## Controlled setup

- Base commit: `520529b` for every arm.
- Model: `deepseek-v4-flash`, temperature 0.
- API: OpenAI-compatible endpoint from local `.env`; secrets never logged.
- Primary arms: separate branches/worktrees; same immutable task and edit/test tools.
- Task: add n8n-like executable workflow system, example/UI/custom types/persistence,
  focused tests, and full verification while preserving drawing-only graphs.
- Usage: provider-reported. Raw totals include cached prompt tokens; uncached figures are
  `total_tokens - cached_tokens`.
- Quality: identical external scorer and hidden acceptance suite.
- Sample size: one primary run per arm. Results diagnose interface behavior, not model
  population variance.

`code-review-graph` index reported commit `bc1640a`, older than the experiment base. Its
structural results remained useful, but index staleness is a confound and likely worsened
that arm.

## What happened

### Baseline

Model used 34 direct reads before writing. Its own tests eventually passed, but typecheck
and hidden acceptance failed: run summaries lacked required status, inspector rows were
missing, type-list shape differed, and missing types did not produce the required blocked
downstream state.

### Generic `context.md`

Context removed four reads and 206,786 raw tokens before edit versus baseline. It raised
quality 15 points and passed typecheck/full suite, but still performed 30 direct reads.
Hidden failures remained around missing run status, inspector rows, and error behavior.

### Code review graph

Model made 17 graph queries, then still made 30 direct reads. It reached first edit latest
among non-projection orientation surfaces, never added its promised test before the turn
cap, and exposed `nodes` in the wrong shape. Structural graph context was too indirect for
this new cross-file plugin; stale indexing further weakened the arm.

### Pure file projections

One crafted projection described ownership, exact source contracts, slots, execution
algorithm, UI, persistence, and test seams. However, ordinary read tools remained visible;
the model reread 29 source files before atomic apply. It finished with the fewest total
tokens and best score among free-form arms, but returned a map-like `nodes` shape instead
of the required array, so hidden acceptance failed.

### Optimization pilots

- Prefetching reduced first-edit work to 1 read and 9,790 tokens, but after editing the
  model spent 42 direct reads and reached the turn cap without tests.
- Dynamic phase tool removal failed: provider responses repeated stale/unadvertised tool
  names. Harness-side rejection reduced successful reads but caused call loops.
- Disabling thinking and forcing a required tool removed protocol drift and reasoning
  tokens, but free-form repair still rediscovered code when read tools had ever appeared.
- A permanent closed loop—projection recipe, atomic apply, focused test, typecheck,
  finish—eliminated rediscovery and completed in five real tool calls.

### File-projection recipe

The recipe reused the independently verified concept slots: system, composition, CSS,
and focused tests. DeepSeek selected one semantic operation, then ran focused, full, and
typecheck verification. Hidden acceptance independently confirmed behavior. This is
equivalent to a high-quality project-local generator/template with source-backed rationale,
not a pretense that the model authored every line.

## Product foundation implemented

Reference worktree now proves one vertical slice toward a general-purpose node editor:

- generic graph data remains unchanged;
- removable `automation` system owns workflow metadata;
- metadata round-trips via `Graph.registerSnapshotExtension('automation', ...)`;
- custom node type registry exposes `registerType`, `configure`, `run`, `reset`, snapshot;
- deterministic DAG execution propagates values and blocks downstream failures;
- cycles and unknown types become visible error states;
- n8n-like example, movable panel, canvas status badges, inspector UI;
- command-driven tests plus hidden acceptance.

This is foundation, not completion of ComfyUI/Blender/n8n/program-flow/UI-builder support.
Next expensive-to-reverse decisions:

1. Define versioned node-type manifest: typed input/output ports, config schema, renderer,
   executor, serialization migration.
2. Split document configuration from transient execution records as reference does.
3. Add async scheduler contract: cancellation, retries, concurrency, streaming/progress,
   deterministic replay.
4. Keep adapters as plugins: n8n/ComfyUI/Blender import-export and runtime bridges must
   not enter graph core.
5. Let UI-building nodes register renderers through the same type manifest, allowing the
   editor to construct its own panels without granting arbitrary core access.
6. Turn this automation projection into a durable repo recipe; add recipes for entity,
   ability, renderer, importer, executor, and test contracts.

## Recommended token-fast workflow

1. Resolve task to one durable concept projection.
2. Prefetch one bounded projection; do not expose tree/search tools initially.
3. Prefer semantic multi-file apply over text surgery.
4. Force immediate focused verification.
5. Unlock at most exact failing origins; cap repair reads.
6. Save a verified change as a reusable recipe only after hidden/full tests pass.
7. Keep raw metrics and score recipe revisions independently; never claim a token win
   without quality parity.

## Limitations

- One model/sample per primary arm; repeat for variance before publishing broad claims.
- Recipe arm has stronger task-specific prior than free-form arms by design.
- Raw token totals count cached prompt tokens; provider billing may discount them.
- Full-suite performance check is load-sensitive. Scorer accepts a parallel-only LCP
  failure only when every other test passes and isolated performance suite passes.
